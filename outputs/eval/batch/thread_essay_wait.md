## Q1  [easy]
Consider a multi-threaded program that guards a shared resource with a pthread-style mutex. Thread A acquires the mutex and is inside the critical section when Thread B reaches the same lock operation. Explain, step by step, what happens to Thread B at the moment it calls the lock, and what must happen when Thread A leaves the critical section, explicitly justifying each step by the kind of waiting mechanism this mutex uses. In your explanation, also state why this approach is described as costly yet convenient for programmers, and briefly relate your steps to the typical mutex usage sequence.

**Answer:** When Thread B calls the mutex lock while Thread A already owns it, B does not spin or repeatedly test; instead, because a mutex belongs to passive waiting solutions, B blocks: it becomes temporarily non‑schedulable (not ready) and relinquishes the CPU until entry becomes possible. This matches the entry behavior: the thread blocks at entry until the critical section (CS) is free.

When Thread A finishes its work in the CS, it performs the exit action by unlocking the mutex. In passive waiting schemes, exit must wake up a sleeping/waiting thread and thereby make the condition to enter the CS true for some thread (possibly B). Consequently, after A unlocks, the system wakes one waiter; B can then be scheduled, acquire the mutex, and enter the CS.

This behavior is reflected in the typical mutex usage sequence: several threads attempt to lock the mutex; only one succeeds and becomes the owner; the owner performs actions in the CS; the owner unlocks; then another thread acquires the mutex and repeats. Because passive waiting causes a blocked thread to relinquish the CPU and later reacquire it, this approach is considered costly in terms of scheduling overhead, yet it is easy for programmers to use because the lock abstracts the waiting/wakeup logic.

In summary: B blocks at entry due to passive waiting; A’s unlock at exit wakes a waiter and makes entry possible; then B acquires the mutex and proceeds—precisely the pattern described by the standard mutex sequence.

## Q3  [medium]

The team has implemented a guard so that at most one thread is inside update() at any time. Under heavy load, they observe that thread W keeps calling the guard but is repeatedly bypassed by other workers that arrive later; however, the system does not freeze—other threads continue to enter and leave update(). Using only the formal progress/safety properties and operational notions provided in the course material, write a short essay that: (a) explains why the team’s current guarantee is insufficient for correctness in this situation, (b) identifies the precise additional requirement that a correct solution must satisfy in this scenario, and (c) ties that requirement back to the exact code region it applies to and the operational behavior needed when a thread leaves that region so that the requirement is actually met. Your answer must reason step by step from the implemented guarantee to the additional requirement, and then to the concrete protected code region, using the formal terminology and entry/exit behavior discussed in class.

**Answer:** The implemented guard enforces only the classic “no two activities are in their protected region at the same time” safety guarantee. That is, it provides mutual exclusion: at any moment, at most one worker can be executing the update() block. While this property prevents concurrent interference, it does not by itself ensure any particular thread will ever get inside.

The observation that worker W keeps attempting to enter but is perpetually bypassed—while other threads continue to enter and leave—shows there is no deadlock (some thread always makes progress), but W is starved. Therefore, beyond mutual exclusion, the solution must satisfy the formal progress property of starvation-freedom: if a specific activity is trying to enter its protected region, that same activity must eventually enter its protected region. In other words, not just “someone gets in eventually” (which is deadlock-freedom), but “the waiting thread itself eventually gets in.” This directly addresses the observed behavior where later arrivals can continually overtake W.

## Q5  [hard]
A team maintains a multi-threaded service that updates a small in-memory table inside a short guarded block. They chose a lock to guard this block. At time t0, Thread A has acquired the lock and is executing those guarded lines. At time t1, Thread B reaches the same lock to run the same block. Later, the service evolves so that an update must touch two shared tables, each protected by its own lock; in one run, Thread A acquires the first lock and then waits for the second, while Thread B acquires the second and then waits for the first. In a concise essay, reason step by step from what using a lock is intended to achieve, to what that choice tells you about the exact code region it protects, to what being inside that region implies about the resource being used, to what happens to Thread B at t1, and finally to why the two-table situation can produce a fatal standstill. Your justification must rely only on the formal safety notion and the operational behaviors described in class, and it must follow the causal order laid out in the scenario.

**Answer:** - First, why a lock here: A lock is used to solve the mutual exclusion problem—ensuring the formal safety property that no two activities are in their critical sections at the same time. This matches the team’s intent for the guarded block (locks are a standard way to enforce mutual exclusion).
- What that tells us about the code region: By that property, the specific guarded lines form the critical section—the exact region to which the “no two at once” guarantee applies, not the whole thread. The guarantee is about that delimited block.
- What being inside implies about resource use: While inside the critical section, the thread is using the shared resource (the in-memory table). That is exactly why exclusivity is required around those lines.
- What happens to Thread B at t1: Because the shared resource is already in exclusive use by Thread A and locking enforces that exclusivity, the lock operation by Thread B blocks its activity when access is not authorized yet. Operationally, B cannot proceed until the lock becomes available, so it is prevented from continuing while A is inside.
- Why the two-table scenario can deadlock: When each thread holds one lock and then waits (is blocked by locking) for the other, the pair circularly block each other. This is the classic deadlock situation described for cooperating activities that share several resources: requesting a lock can become fatal because neither can progress while waiting for the other’s lock.
